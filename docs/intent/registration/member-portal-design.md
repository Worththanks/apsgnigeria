# Low-Level Design: APSG and CWDI Member Portal

## Scope

Route member login and registration-number recovery to the matching organization registry, render that organization’s member details, and let verified members maintain an allowlisted part of their own profile. APSG records use `public.members`; CWDI records use `public.cwdi_members`. Administrative access and registration submission are outside this component.

## Login and Session

- Choose the registry from the registration-number prefix: `CWDI/` selects `cwdi_members`; other accepted member numbers retain the existing APSG `members` lookup.
- In member login, registration-number recovery, and recovery-candidate phone confirmation, provide an accessible calling-code selector backed by the same local international phone metadata as registration. Display the calling code before the country name in each option so it stays visible on narrow screens. Default the calling code to Nigeria (`NG`, `+234`); accept either a national number interpreted with the selected calling code or a complete `+` E.164 number. Keep phone calling code independent from residence and never infer it from residence, browser location, locale, or IP address. The administrator email/password path does not use phone parsing or the calling-code selector.
- Validate each phone input locally and send one canonical E.164 value to the verification or lookup operation. Reject malformed numbers before making a request; do not send browser-generated phone-candidate arrays.
- Match the registration number and canonical phone only within the selected organization. Use `apsg_member_login_by_reg_phone` for APSG and `cwdi_member_login_by_reg_phone` for CWDI; the browser never reads either member table to verify a login. Each operation validates E.164 and compares the complete calling code and national number after removing presentation separators from stored values. For a submitted Nigerian `+234` value, also recognize the same complete Nigerian national significant number stored with or without one domestic leading `0`. Never compare suffixes or interpret an unprefixed non-Nigerian number using an assumed country.
- Localhost login and verified registration handoff use the same organization-specific phone-verification operation and full-number comparison as production, but retain view-only access without a write-capable credential. Do not use a direct browser table query as a substitute when an operation is unavailable.
- Attach the allowlisted source name to the verified member session so the details page refreshes from the same registry.
- Keep the existing member-session flow and registration-number-plus-phone verification.
- Preserve the existing registration-number-plus-phone sign-in interaction. In production, route verification through an organization-aware session Edge Function that checks only the selected registry, returns the matching member record, and issues a signed member credential valid for 30 minutes. Bind claims to issuer, audience, member ID, organization, permitted basic-profile/photo-write scope, issue time and expiry; do not include the raw phone number or registration number. In localhost preview, retain verified view-only access without issuing a write-capable credential.
- When the registration candidate flow has verified an existing member for general membership, exchange the registration number and canonical E.164 phone held in the current form flow with the same session Edge Function before opening the portal. The function re-verifies them server-side using the selected registry's full-number comparison and returns the scoped credential without asking the member to enter them again. Do not treat the browser's verified flag or member object as authority. In localhost preview, preserve the verified view-only handoff and do not issue a write-capable credential.
- Store the signed credential in session storage alongside the member view state; the stored member object, the legacy `apsg_member_portal_verified` flag and URL parameters are not proof of write authorization. Expired or invalid credentials require the member to sign in again before a write.
- `member-profile-update` and `member-photo-replace` Edge Functions verify the signed credential and derive the registry and member row from its verified claims. A credential grants only the documented basic-profile and photo operations; it does not grant admin access or edits to protected membership data. Keep signing and service-role secrets in function configuration, and use an idempotency key for each photo replacement request.
- Rate-limit session verification and member writes by appropriate account and request signals, return generic sign-in failures that do not reveal whether a registration number exists, and never log credentials, phone numbers or registration numbers.
- Localhost member preview does not obtain a write-capable credential. Its page controls remain disabled, and local build configuration does not enable member-write calls. Origin checks are an environment guard, not a substitute for verifying the signed credential.
- Treat `mode` and `source` URL parameters as navigation hints only. Member writes require the member credential; admin writes continue to require existing admin authorization.

## Registration-Number Recovery

- Search both organizations independently by the submitted canonical E.164 phone using `apsg_find_members_by_phone` and `cwdi_find_members_by_phone`. Each organization applies the complete-number and legacy Nigerian comparison defined above; never query one registry through the other organization's operation or merge records across registries.
- Treat location details as optional candidate-ranking hints, not phone identity or authorization. The optional residence-country selector starts blank and is independent from the phone calling-code selector. For a member who selects Nigeria as current residence, use the existing State/LGA/Ward controls. For a non-Nigerian residence, collect the explicit country and current city/state-province; keep any Nigerian home State/LGA/Ward separate. A member may search by phone without location details, and a location change or mismatch must not suppress a full phone match.
- Keep unverified residence on historical rows unknown. Do not infer current residence from the stored Nigerian State/LGA/Ward, phone number, registration number, or a browser setting. If those historical location fields are used as recovery hints, label and treat them as recorded local-area details rather than current residence.
- Snapshot the canonical E.164 phone and any location hints for each recovery request. If the phone, calling code, or a location hint changes while a query or candidate confirmation is pending, discard the stale results and candidate state; a new request uses only the current values.
- Keep up to three candidates per available registry, ranking location-hint matches ahead of other phone matches and then by newest record. Show candidates sequentially with their organization and source-specific location labels so a member registered with both organizations can identify each record; do not let one registry's candidates displace the other registry's results.
- After the member confirms a candidate and re-verifies its phone using the canonical E.164 value, show only that candidate's organization registration number and continue through the same organization-aware sign-in path.
- If one registry query is unavailable, preserve candidates from the available registry, identify the unavailable organization and offer retry for that query. Do not claim that no record exists in both organizations unless both registry queries succeeded and returned no candidates. Report recovery as unavailable only when neither registry can be queried.

## Member Details

- Show current residence from the verified residence fields. For `NGA`, show Nigeria and the current Nigerian State/LGA/Ward. For another country, show its country, city and state/province, then show any Nigerian State/LGA/Ward separately as Nigerian home location. Resolve country labels from the shared local country metadata. If the residence country is missing, show it as not recorded; never infer a current residence from legacy location, phone or registration number.
- Show contact values by role from the verified member record, regardless of current residence: the primary phone remains the account-identity phone, and a populated `nigerian_phone_e164` is labeled as the Nigerian contact number. Show the secondary number and `preferred_contact_type` together only when the stored number is valid Nigerian E.164 and the preference is `primary` or `nigerian`; render the preference as a readable label (`primary` as “Primary phone” or `nigerian` as “Nigerian contact number”). Use the same labels in the member-facing copied summary. If no Nigerian contact number is stored, show the primary phone as the only available contact and omit the empty secondary number and preference. If the stored pair is inconsistent, show only the primary phone and the existing profile data-error feedback; do not infer a preference. Do not use the Nigerian contact number for login, recovery, lookup or account verification.
- Show stored Middle Name and Gender in Personal Information and the copied summary, with an em dash for missing values. Compose full names from first, middle and last name. Gender reads the existing `sex` field.
- In production, refresh a verified member record from the registry selected by its registration number or allowlisted session source. Include `nigerian_phone_e164` and `preferred_contact_type` only in the server-owned, verified member-view response allowlist used by session and refresh paths. Keep both values out of signed credential claims, URLs, logs and profile/photo write responses. In localhost preview, render them from the verified session snapshot directly without waiting for a duplicate registry request or third-party script download.
- The administrator route guard excludes only `/admin/member-details.html` with `mode=member`; that view uses its own member-session gate and cannot perform administrator operations. Administrator mode on the same page continues through the administrator session and role checks.
- Use the organization’s name and logo on the member-facing confirmation view.
- In member mode, present a focused, organization-branded profile with the member identity, key profile facts, documents, and account details in a clear reading order. Use the existing record values; do not add or imply new metrics.
- Provide one clearly labeled Edit profile action for member-mode personal details. It switches the Personal Information card between read-only display and an inline form with Save and Cancel actions. The form edits first name, middle name, last name, gender (`sex`) and email. Current residence, Nigerian home location, primary phone, Nigerian contact phone, contact preference, designation, registration date, registration number, PVC/APC identifiers and uploaded identity documents remain read-only in this form; residence correction belongs to the authorized admin workflow.
- Profile Save validates the editable fields, sends only changed allowlisted fields, reports success or failure beside the form, and updates the displayed profile only after the organization-specific write path confirms success. If a write response omits read-only contact fields, merge the confirmed changes with the verified profile snapshot or refresh from the selected organization; never treat omitted contact properties as `null`. Cancel discards the draft. Leaving with unsaved changes requires confirmation before discarding. A stale-record conflict retains the draft and requires refresh or reconciliation against the current saved record.
- Keep the edit state inside the Personal Information card rather than opening a second page or modal. At phone widths, use full-width fields and reachable Save and Cancel actions; preserve clear field labels, validation feedback, visible focus and the existing brand surfaces.
- Allow profile-photo replacement from the organization-branded identity panel. Show a local preview and Save/Cancel controls before upload. Accept JPEG, PNG or WebP images up to 3 MB and validate image content again on the server. Disable duplicate submissions while upload is in flight. Upload to a unique server-generated object key first, update the member's profile path only after upload succeeds, and retain the old path until the database update commits. On update failure, keep the old photo active and remove the new object best-effort; if cleanup fails, leave it for maintenance. After a successful update, remove the old object best-effort only if it is under that member's profile path. Cancel is unavailable once upload begins and does not imply rollback.
- Route profile updates and photo uploads through Supabase Edge Functions. Each function verifies a short-lived signed member credential and derives one organization registry from verified claims. Keep the service-role secret in function configuration, apply a fixed editable-field allowlist, and never accept a table name, member ID or storage path as authority from the browser. Do not fall back to direct browser table updates or anonymous storage uploads if a function is missing or fails.
- Use a revision precondition such as the stored `updated_at` value for every profile write. Return a conflict if another member or administrator changed the record after the draft was loaded. Return stable outcomes for expired credentials, forbidden fields, validation errors, conflicts, rate limits and service failures.
- On a timeout or unknown response, preserve the draft and refetch the authoritative record before retrying; do not report a definite failure or success until the server state is reconciled. Disable duplicate saves while a request is in flight. If a write returns a conflict, retain the draft, show the latest server values and require an explicit refresh/reconcile action before another save.
- For photo replacement, validate actual file content, size and supported image type on the server; generate a unique object key under the authenticated member's own organization/member path; upload the new object; then update the database pointer with the same revision check. Keep the prior object until the pointer update commits. If the pointer update fails, keep the old photo active and best-effort remove the new object. After commit, best-effort remove the prior object only when it is inside that member's allowed path. A cleanup failure after commit does not undo the saved photo; report the photo as saved and record cleanup for maintenance. Once upload starts, hide or disable Cancel and communicate that the save is in progress.
- Keep phone changes outside the general profile form. A separate phone-change flow must verify control of the proposed number before it replaces the login number; until an approved verification channel is configured, leave the saved phone unchanged and state that phone changes are unavailable. Defer any additional next-step help copy until a verification channel is selected.
- Keep member mode visually distinct from the admin dossier: omit the Record Summary (including PVC/APC status, record-health and dossier-readiness metrics, and admin contact actions), Checklist & Audit Trail, and other admin-only review controls. Preserve those panels and their behavior in admin mode. When Copy is activated during an unsaved profile edit, copy only saved verified profile values, never the draft; announce copy success or clipboard failure through accessible feedback.
- Hide the public-site footer in member mode and provide one clearly labeled Home action linking to `/` at every viewport width. Keep member login navigation, Copy, and Print actions available; Home navigation does not log the member out or change the displayed record.
- Use a compact responsive profile header and card layout. At phone widths, stack profile content into one readable column, keep the Home label visible, wrap header actions as needed, and prevent horizontal page scrolling. At all sizes, keep controls fully visible and at least 44px high, show keyboard focus, and allow long names, registration numbers, addresses, and filenames to wrap without clipping.
- Use meaningful organization-specific alternative text for logos and textual status labels that do not depend on color alone. When photos or documents are missing, show a compact placeholder; when profile data fails to load, keep Home navigation available and show the existing error feedback.
- Use the same self-service profile and photo capabilities for APSG and CWDI, with each write confined to the verified member's own registry. Keep CWDI bank details read-only until a CWDI-specific secure write endpoint is available. Keep administrative editing behind existing admin authorization.
- Preserve APSG bank-detail editing through its existing `update_member_account_details` RPC, separately from the new basic-profile/photo allowlist. If that RPC is unavailable, show a clear save error; never fall back to a direct browser table update. Keep CWDI bank details read-only until a CWDI-specific secure write endpoint is available.
- When the member portal is served from localhost, allow a verified member to view the organization-specific member record but disable member self-service edits and file uploads for every organization. Local preview must not mutate the production database or storage.
- Enable row-level security on `cwdi_members`, grant direct table access only to authenticated users, and require `is_admin_at_least('admin')` for every direct admin operation. Public registration, lookup, verification, and Youth Wing updates use only the narrow CWDI-specific SECURITY DEFINER RPCs.
- Preserve APSG member self-service behavior and current admin controls.

## Decisions and Alternatives

| Decision | Chosen | Alternative | Rationale |
|---|---|---|---|
| Registry routing | Derive the allowlisted table from the organization-specific registration number and verified session source | Query both registries during every login | A prefix selects one registry directly and avoids treating organization identifiers as interchangeable. |
| Phone entry | Use a local-metadata calling-code selector, defaulting to Nigeria, and send one validated E.164 number for login and recovery | Require digits-only local input or infer country from residence | Diaspora members can use their current phone while Nigerian users keep the familiar default; phone country remains independent from residence. |
| Phone identity matching | Compare complete E.164 values server-side and explicitly convert recognized Nigerian national legacy formats for `+234` submissions | Compare final digits or query raw phone candidates in the browser | Complete-number matching prevents international collisions while preserving legacy Nigerian accounts without guessing a country for other national-format values. |
| Recovery search | Search both registries independently with organization-specific RPCs, label every candidate, and report partial availability | Ask the user to choose an organization or fall back to a browser table read | One phone search remains convenient for members in either or both organizations while preserving source boundaries and honest results when a registry is unavailable. |
| Recovery location | Use optional residence-specific location hints for candidate ranking; keep Nigerian home geography separate and permit phone-only search | Require Nigerian State/LGA/Ward for every candidate | Diaspora applicants may have no Nigerian location fields, and existing rows may not have verified residence; location must help find a candidate without becoming an assumed identity or residence. |
| Recovery candidate list | Keep up to three candidates per successful registry, rank location matches first and newest records second, and reveal an ID only after full phone verification | Use one combined three-candidate limit or reveal IDs before phone verification | A popular phone or one registry's duplicate rows must not hide the other organization's record; the phone verification remains the proof before exposing the registration number. |
| Organization member changes | Use independently verified APSG and CWDI write paths for allowlisted profile fields and profile photos; preserve the current APSG bank-details edit path and keep CWDI bank details read-only | Reuse APSG writes against CWDI or update either registry directly from the browser | Each organization retains its own data boundary, while the member self-service capability remains consistent. |
| Local member portal | Allow verified members to inspect their record in view-only mode | Disable portal access locally or allow production writes from a local preview | Local review should use the real portal view while retaining the preview's no-write boundary. |
| Member-mode content hierarchy | Show member-facing identity, profile facts, documents, and account details; keep internal verification and audit panels in admin mode | Reuse the complete admin dossier for members | Member access is for reviewing one's own record; internal review material adds clutter and exposes operational context that is not part of the member profile. |
| Member-mode exit navigation | Hide the public footer and keep a labeled Home action in the portal header | Retain the long public footer or rely on browser navigation | A direct Home action gives members a predictable exit while the footer adds unrelated site navigation to a focused portal. |
| Responsive member layout | Use a compact single-column phone layout with proportionate identity imagery and reachable actions | Preserve the desktop card density on smaller screens | The portal is primarily used on phones; identity and core record details must remain readable without horizontal scrolling. |
| CWDI data access | Allow direct browser access only to authenticated admins whose active role passes `is_admin_at_least('admin')`; use specific SECURITY DEFINER RPCs for public registration and verified member lookup | Grant browser roles direct table access or query CWDI data through APSG RPCs | Row-level security protects the registry while preserving the existing registration and portal flow. |
| Member profile updates | Issue a short-lived signed member credential after organization-aware registration-number-plus-phone verification; require it at every server-side profile or photo write and derive one registry/member from verified claims | Trust the browser's session record, send reusable identity values with every update as ownership proof, accept caller-selected tables or paths, or permit direct anonymous writes | A signed credential provides bounded write authority after the existing identity check; verified claims bind the write to one member and one organization without trusting browser-supplied IDs. |
| Verified registration handoff | Silently exchange the verified general-membership candidate through the member session endpoint and open the portal without a second login prompt | Trust browser-side candidate verification as write authority or ask the member to re-enter the same registration number and phone | Server-side re-verification preserves the existing handoff while ensuring browser-controlled state cannot authorize member writes. |
| Write endpoint runtime | Use organization-aware Supabase Edge Functions with server-only signing/service-role secrets for session issuance, profile-field updates and photo replacement | Put a service-role or signing key in the browser, use member session storage alone as proof, or upload anonymously to Storage | Supabase already owns the member data and photo bucket; Edge Functions can verify the signed member credential and ownership before privileged access without exposing secrets to the public page. |
| Residence on member profile | Show verified current residence separately from Nigerian home location; unknown legacy residence remains unrecorded | Infer residence from legacy State/LGA/Ward or phone, or reuse Nigerian fields for a foreign address | Current residence supports diaspora membership while preserving the meaning of historical Nigerian geography. |
| Contact numbers in member mode | Display the primary phone and a valid optional Nigerian-contact/preference pair by role; keep both secondary fields read-only and include them only in verified member-view responses | Hide the secondary value or use it as another login/recovery phone | Members can see how they can be contacted without changing the existing primary-phone identity and verification contract or exposing contact values in credentials and write responses. |
| Editable profile fields | Allow names, gender and email in member mode; keep residence, Nigerian home location, both contact values, designation, membership identifiers, documents and membership classification admin-managed | Let members edit residence and all location fields, or make every profile field admin-only | Members can correct basic personal details while authorized admins retain control of residence classification and location reporting. |
| Local member edits | Keep localhost member preview view-only and block writes and uploads | Allow browser-local draft changes or connect local preview to production writes | Local review must not imply that member changes were saved or mutate production data. |
| Bank details | Preserve the existing APSG member bank-edit behavior; keep CWDI bank details read-only until its own secure endpoint is available | Remove APSG bank editing as part of profile changes or share the APSG write path with CWDI | The requested basic profile and photo scope should not regress the existing APSG capability or cross the CWDI organization boundary. |
| Member-write credential | Use a 30-minute signed credential with an issuer, audience, member subject, organization, narrow write scope, issue time and expiry; require sign-in again after expiry | Treat browser session flags, profile JSON or identity fields as authorization | A limited lifetime and explicit claims keep the member write authority scoped and make the expiry behavior understandable. |

## Edge-Case Probe

| Condition | Required handling |
|---|---|
| A person has an APSG and CWDI record sharing the same phone number | Preserve both candidates and display the organization name with each. |
| Two international numbers have the same final 10 digits but different E.164 values | Treat them as different identities in login, recovery, and handoff; never match by suffix. |
| An existing Nigerian phone is stored as a national number with a leading `0` or without it | Match only the equivalent submitted `+234` value by comparing the complete national significant number. |
| A non-Nigerian E.164 phone has the same last digits as an unprefixed national-format stored phone | Do not match it; do not infer a country from residence or browser settings. |
| A member's residence-country filter differs from the selected phone calling code | Keep both values independent; do not change either choice or infer identity from the difference. |
| A diaspora member searches for a forgotten registration number | Allow current residence country, city and state/province as optional candidate hints; do not require Nigerian State/LGA/Ward. |
| A legacy row has no verified residence country | Leave it unknown; do not derive current country from its Nigerian home State/LGA/Ward or phone. Permit the full-phone match to remain a recovery candidate without a residence value. |
| A member opens a profile whose residence country is not recorded | Show residence as not recorded; do not present legacy State/LGA/Ward, phone or registration-number segments as current residence. |
| An `NGA` member profile has State/LGA/Ward values | Show them as current Nigerian residence, separately labeled from foreign-residence fields. |
| A non-Nigeria member profile also has Nigerian State/LGA/Ward values | Show country/city/state-province as current residence and label the Nigerian fields as home location. |
| A verified member has a stored Nigerian contact number and contact preference | Show the optional number and selected preference separately from the primary account phone; do not use it for login, recovery or identity matching. |
| A member has no stored Nigerian contact number | Show the primary phone as the only available contact and omit empty secondary contact and preference values. |
| A verified member response contains an invalid Nigerian secondary number or unsupported/missing preference | Show only the primary phone and the existing profile data-error feedback; do not show the secondary value or infer a preferred contact. |
| A profile-write response omits the read-only contact properties | Preserve them from the verified snapshot or refresh from the selected organization; do not interpret omission as clearing the saved values. |
| A member-view response or write path is assembled | Include contact values only in the verified member-view payload; exclude them from credential claims, URLs, logs and profile/photo write responses. |
| A member copies a summary while profile edits are unsaved or clipboard access fails | Copy only saved verified values and announce success or failure through accessible feedback; never copy the unsaved draft. |
| A member attempts to change residence or Nigerian home location in self-service | Keep those values read-only; require an authorized admin workflow, and preserve the issued registration number. |
| A member's current residence has changed since registration | Do not reject the phone match because a location hint differs; require the organization registration number and full phone verification before revealing the registration number. |
| Several phone matches exist in each organization | Keep up to three candidates per organization, rank location matches before newer records, show source organization, and do not expose registration numbers before full phone verification. |
| A recovery phone, calling code, or location hint changes while search or confirmation is pending | Discard the stale results and candidate verification state; use only the current request snapshot. |
| A login, recovery, or candidate-confirmation form contains an invalid phone | Reject it before any registry operation and show an accessible field-specific error. |
| An administrator signs in with an email and password | Keep the admin path unchanged and do not parse the password as a member phone or apply the calling-code selector. |
| The CWDI or APSG recovery RPC is unavailable while the other registry query succeeds | Keep the available registry's candidates, identify and allow retry of the failed organization, and do not state that both organizations have no match. |
| Both recovery queries succeed and find no candidates | Show that neither registry found a matching number; do not redirect into an unverified member session. |
| The CWDI table or its recovery RPC is unavailable | Never query `cwdi_members` directly from the browser; preserve any APSG results and identify CWDI as unavailable. |
| The CWDI table or verification RPC is unavailable during CWDI login | Show the normal login failure and do not query APSG using the CWDI registration number. |
| The APSG login or verification RPC is unavailable | Fail login with the generic member error and do not query `members` directly from the browser. |
| A CWDI member opens a member-details URL directly without a verified session | Keep the existing member-login gate; do not load the record from the URL alone. |
| A general-membership candidate has been verified by registration and is handed to the production member portal | Re-verify the registration number and phone through the member session endpoint, issue the scoped credential, and open the portal without another prompt; the browser-side handoff alone grants no write access. |
| A verified registration candidate is handed to the portal with an international phone | Pass the canonical E.164 value and re-verify the complete number in the selected organization's operation before issuing a credential. |
| The production session endpoint cannot exchange a verified registration handoff | Keep the verified candidate in the current page, show a retryable portal-entry error, and do not open a production member session without the signed credential. |
| Registration number and phone do not verify, or the sign-in endpoint is rate-limited | Return a generic sign-in failure that does not reveal which identifier was found; do not issue a write credential. |
| A browser calls a member-write endpoint without a credential, with an expired credential, or with a credential for another organization/member | Reject before reading or writing a member record; do not fall back to URL parameters, stored member JSON, or caller-supplied IDs. |
| A member changes `mode` or `source` URL parameters or replays an old browser-side verified flag | Treat URL values and the flag as navigation hints only; resolve access from the signed credential and authenticated admin authorization. |
| A CWDI member edits basic profile details or a profile photo | Use the CWDI-specific write path and update only `cwdi_members`; keep bank details read-only until a CWDI-specific bank endpoint exists. |
| An administrator opens a CWDI dossier | Retain the existing admin authorization and source-table routing; the `cwdi_members` RLS policy must independently require an active admin role. |
| A verified member edits profile details | Permit only the documented fields through the endpoint for that member's registry; do not change protected fields or another organization's record. |
| A profile write endpoint is missing, unavailable or returns an error | Keep the saved profile unchanged, preserve the member's draft, show a retryable error, and never fall back to a direct browser table update. |
| The existing APSG bank-detail RPC is unavailable | Keep the current bank values, show a clear save error, and do not use a direct table-update fallback. |
| A write credential expires while a member is editing | Preserve the draft, require sign-in again, and submit only after a fresh credential is issued. |
| Two profile writes race or the record changes after the form loads | Reject the stale revision with a conflict; keep the draft and latest server values visible until the member explicitly reconciles them. |
| A write times out after the server may have committed it | Preserve the draft, refetch the member record, compare authoritative values and revision, then show the reconciled result before allowing another save. |
| A member profile is edited in localhost preview | Keep the page view-only and issue no profile write, database update or storage upload. |
| A member selects an invalid, unsupported or oversized profile image | Reject the selection, retain the current saved image, and explain the accepted image formats and 3 MB limit. |
| A photo upload succeeds but the profile-path update fails | Keep the existing image path active, retain an actionable failure state, and best-effort clean up the unreferenced new object. |
| A photo pointer commits but removal of the old object fails | Show the new photo as saved; record old-object cleanup as maintenance work and do not revert the committed pointer. |
| A member tries to cancel or submit twice during photo upload | Prevent duplicate submissions; once upload begins, explain that the save is in progress and do not imply that Cancel can roll it back. |
| An administrator changes a profile field while the member has an unsaved draft | Detect the stale record version before saving and require refresh or reconciliation instead of silently overwriting the newer value. |
| A member requests a phone-number change before a verification channel is configured | Do not change the login phone; explain that the proposed number must be verified before it can be saved. |
| A member opens the portal on a narrow phone viewport | Keep the organization identity, Home action, member details, and supported actions visible and readable without horizontal scrolling. |
| A member uses the portal's Home action | Navigate to `/` without changing the verified member record or session data. |
| A member views a long name, registration number, address, or filename | Keep the complete value readable by wrapping it without clipping controls or creating horizontal page scrolling. |
| A member has no profile photo or uploaded document | Show a compact placeholder without leaving a broken image or oversized empty region. |
| An administrator opens the same member-details route | Retain the admin dossier, internal review panels, public-site navigation controls, and existing admin actions. |

## Open Questions & Future Decisions

### Resolved

1. ✅ Member self-service covers basic personal details and profile photos for APSG and CWDI; protected identifiers, uploaded evidence and membership decisions remain admin-managed.
2. ✅ Localhost member preview remains view-only.
3. ✅ Preserve APSG member bank editing through its existing RPC; CWDI bank details remain read-only until a CWDI-specific secure endpoint is available.

### Deferred

1. Phone-number verification provider and delivery channel must be selected before the separate phone-change flow can persist a new login number.
2. Until a verified delivery channel is configured, the phone-change flow remains unavailable and the current number cannot be changed; defer additional help copy until a channel is selected.
3. The local SQL sources do not define the APSG lookup and registration-number-and-phone verification RPCs. Before implementation, locate their authoritative migration source or add local migration definitions that follow the organization-specific E.164 contract.
4. The admin member editor must own existing-member residence corrections; its separate member-administration design must define the authorized edit path and preserve issued registration numbers.
